# Architecture Decisions and Trade-offs

| Decision | Chosen approach | Alternative considered | Benefit | Limitation or risk |
|---|---|---|---|---|
| Application shape | One FastAPI monolith | Multiple services or workers | One process is fast to build, run, test, and explain while preserving internal boundaries. | Components do not demonstrate independent scaling or deployment. |
| Browser UI | Thin static HTML/JavaScript served by FastAPI | React application | Avoids a second toolchain and keeps effort focused on traces, agent behavior, and safety. | Less component structure and visual polish. |
| Trace storage | In-memory repository behind an interface | SQLite, production database, or JSON persistence | Minimal setup, isolated tests, and a clear replaceable boundary. | Runs disappear on restart and the adapter is single-process only. |
| Agent topology | One bounded investigator | Multiple specialist agents | Makes tool selection and reasoning easy to inspect without coordination overhead. | One context must handle the entire small diagnosis task. |
| Investigator tools | Four consolidated read-only tools | Separate extraction, validation, ERP, policy, and runbook tools | Reduces overlap while preserving genuine information selection. | `get_stage_artifact` is broader and must enforce a strict stage enum and bounded response. |
| Runbook retrieval | Local tagged entries with exact and lexical ranking | Embeddings and vector RAG | Transparent, deterministic, dependency-light, and appropriate for a tiny corpus. | Does not handle large corpora or semantic paraphrases as well. |
| Scenario input | Presets populate an editable textarea and ERP behavior | Locked presets or unrestricted input without fixtures | Combines reproducible demos with genuine live custom extraction. | A selected preset no longer guarantees its named result after the text is edited. |
| Scripted provider | Recognized fixtures only; reject edited custom input | Heuristic parser or silently reusing preset output | Keeps offline tests deterministic and avoids misrepresenting scripted behavior as AI. | Custom experimentation requires credentials and the live provider. |
| Primary AI path | Real LLM for extraction and investigation | Scripted behavior only | Demonstrates actual interpretation, tool choice, and structured reasoning. | Adds cost, latency, credentials, and model variability. |
| Validation boundary | Structural/type, deterministic domain, and deterministic business-rule validation are separate | One Pydantic schema or one combined validator | Makes ownership and failure semantics precise: optional extraction fields do not bypass required business checks. | Adds more models and transitions to a small workflow. |
| Canonical errors | Deterministic workflow owns and hides them from the investigator | Pass the error code or full summary directly to the model | Forces evidence gathering and prevents model output from becoming authoritative. | Investigation takes more calls and may disagree with the known workflow classification. |
| Recovery authority | Deterministic policy authorizes `ALLOW`, `BLOCK`, or `REQUIRE_REVIEW` | Let the investigator execute its recommendation | Contains hallucinations and makes policy behavior fully testable. | The agent cannot dynamically handle novel recovery actions. |
| Recovery execution | One bounded, idempotent retry for transient ERP 503 | General autonomous remediation or recommendation-only MVP | Demonstrates a real safe side effect with a narrow blast radius. | Does not prove broader compensation, rollback, or approval workflows. |
| Human handling | `REQUIRE_REVIEW`; corrections create a new run | Action-approval terminology or mutating/resuming the failed run | Accurately describes missing-data handling and preserves audit history. | There is no in-app review queue or linkage workflow beyond trace metadata. |
| Trace quality | Intentionally include continued and recovered warnings before a terminal ERP failure | Clean traces containing only the root cause | Demonstrates evidence discrimination instead of simple error-keyword matching. | Scripted tests can appear staged; an opt-in live evaluation is still needed. |
| Investigation trigger | Explicitly investigate a failed run | Automatically invoke the LLM for every failure | Lets reviewers inspect the raw failure first and avoids unnecessary cost. | Adds one user action to the demo flow. |
| Agent limits | Three model turns and six read-only tool calls | Open-ended agent loop | Prevents runaway cost, loops, and excess data exposure. | A model may fail to finish even when more calls could have helped. |
